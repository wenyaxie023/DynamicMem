# Dynamic Profile Human Validation Instructions

## What Are We Building?

We are creating **synthetic dynamic user profiles** - detailed, realistic simulations of how people's lives evolve over time across different life domains.

### Why This Matters

These profiles will be used to:
- Generate user dynamic trajectories for evaluating dynamic longitudinal user modeling
- Test personalization algorithms in realistic scenarios
- Research how well personal agents can adapt to evolving user needs and contexts over time

**Quality is critical** - profiles must represent realistic, coherent, livable human lives with plausible progression patterns.

## Understanding the Context Materials

The validation platform provides two key reference documents that you **must use** to evaluate profile quality:

### 1. Basic User Profile (Structured Data)
Structured demographic and contextual data about the user (age, occupation, income, work hours, household composition, etc.) - use this to verify that profile details respect realistic constraints and resources.

### 2. World Background (External Context)
A timeline of external events, seasons, and societal factors during the profile period - many changes in the dynamic profile are motivated by these external factors, and you should verify the causal connections make sense.

## How These Materials Work Together

**Validation Flow:**
1. **Read Original Description** → Understand who the user is
2. **Review Basic Profile** → Know their constraints and resources  
3. **Check World Background** → Understand what external factors drive changes
4. **Evaluate Dynamic Profile** → Verify it's realistic given #1-3

**Example:**
- Original: "28-year-old teacher, recently adopted a dog"
- Basic Profile: Income $45K/year, works 8AM-4PM weekdays, rents apartment
- World Background: Window w1 is winter (Dec-Feb), Window w3 is summer (Jun-Aug)

**Valid profile evolution:**
- w1: Acquires "morning_dog_walk" at 6:30 AM (before work), buys budget dog food, prefers indoor activities (winter)
- w3: Adjusts "morning_dog_walk" to 6:00 AM (summer sunrise earlier), shifts preference to outdoor park activities (summer weather)

**Invalid profile evolution:**
- w1: Buys $3000 purebred dog + premium equipment (exceeds income constraints)
- w3: Still maintains aggressive winter indoor routine despite summer weather (missing follow-up)
- Schedules "morning_dog_walk" at 8:30 AM (conflicts with work start time)

## Your Task

Using these reference materials, validate that the generated dynamic profile:
1. **Respects realistic constraints** (Basic Profile)  
2. **Responds appropriately to external factors** (World Background)
3. **Forms a coherent, livable life narrative** (overall realism)

## Profile Structure Overview

### Profile Structure

Each complete dynamic profile consists of:

**Basic User Profile (Read-Only Context)**
You'll see this as reference, but **do NOT edit** it.


**Domain-Specific Dynamic Profiles (Your Validation Target)**
Each domain contains three types of evolving content:

1. **User Attributes** - Factual, discrete properties
   - Examples: "owns iPhone 14", "job_title: Software Engineer", "family_members: [partner, child age 5]"
   - Format: Always lists of concrete values

2. **Habits** - Structured recurring behaviors
   - Examples: "morning_dog_walk", "weekly_meal_prep", "evening_gym_sessions"
   - Format: JSON objects with 5 required fields:
     - `action`: What they do (e.g., "walk_dog_on_leash")
     - `frequency`: How often (e.g., "daily", "3_times_per_week")
     - `timing`: When (e.g., "early morning before work (6:00-6:30 AM)")
     - `context`: Where/how (e.g., "around the neighborhood for 20-30 minutes")
     - `description`: Natural language summary (5-20 words)

3. **Preferences** - Subjective inclinations
   - Examples: "prefers outdoor exercise over gym workouts", "prefers long-term investments over day trading"
   - Format: Concrete descriptions of relative preferences (5-20 words)

### Time Windows Structure
- initial_state: Baseline at time zero
  - Contains: user_attributes_state.initial, habits_state.initial, preferences_state.initial
  - Required: `summary` field synthesizing the baseline

- time_windows (w1, w2, w3...): Sequential evolution
  - Each window contains:
    - `window_id`: Identifier (e.g., "w1", "w2")
    - `time_range`: Date range (e.g., ["2024-03-01", "2024-05-31"])
    - `window_description`: **What drives changes** in this period (external factors, user motivations)
    - `user_attributes_delta`: Changes to attributes (add/remove/modify operations)
    - `habits_delta`: Changes to habits (acquire/adjust/drop operations)
    - `preferences_delta`: Changes to preferences (shift/amplify/attenuate operations)
    - `summary`: Synthesis of all changes in this window



## Introduction to Validation

You are validating **dynamic user profiles** - detailed simulations of how a person's life evolves across multiple domains (Work & Education, Health & Wellness, Family & Close Relationships, etc.) over time windows.

Your task is to catch errors and revise them to ensure the profile represents a **realistic, coherent, livable human life**.


## What to Check: 8 Categories of Issues

### Category 1: Structural Missing Fields

**What to look for:** Required fields that are missing from the JSON structure

**Common violations:**

a) **Missing required fields in habits**
- Every habit must have all 5 fields: `action`, `frequency`, `timing`, `context`, `description`
- Check both initial_state habits and habits in delta operations

b) **Missing summary fields**
- `initial_state` must have a `summary` field
- Every time window must have a `summary` field

c) **Missing window_description**
- Every time window must have a `window_description` field

d) **Missing reason fields**
- All delta operations (user_attributes_delta, habits_delta, preferences_delta) must have a `reason` field explaining the change

e) **Incorrect null format for dropped habits**
- When a habit is dropped, `new_state` must be JSON `null` (not the string `"none"` or empty string `""`)

**How to check:**
1. For each habit in initial_state and in habit deltas, verify all 5 required fields exist
2. Scan for missing `summary` in initial_state and each time window
3. Scan for missing `window_description` in each time window
4. Check that every operation in deltas has a `reason` field
5. For drop operations, verify `new_state` is `null` not `"none"`

**How to fix:**
- Add the missing field with appropriate content
- For habits: ensure the description is 5-20 words and accurately summarizes the habit
- For summaries: synthesize a 2-4 sentence description of the state/changes
- For window_description: identify external factors (seasons, events) and internal motivations driving changes
- For reasons: explain why this specific change occurred in this window
- For dropped habits: replace `"none"` with JSON `null`

**Example fix:**
```json
// BEFORE (missing description)
"morning_jog": {
  "action": "jog_outdoors",
  "frequency": "3_times_per_week",
  "timing": "6:00-6:45 AM",
  "context": "around the neighborhood park"
}

// AFTER (description added)
"morning_jog": {
  "action": "jog_outdoors",
  "frequency": "3_times_per_week",
  "timing": "6:00-6:45 AM",
  "context": "around the neighborhood park",
  "description": "User jogs around the park three mornings per week for cardiovascular fitness"
}
```



### Category 2: Missing Prior Existence for Modifications

**What to look for:** Operations that modify/adjust/shift something that was never defined before

**The rule:** 
- `modify/delete` (for attributes), `adjust` (for habits), and `shift`/`amplify`/`attenuate` (for preferences) can ONLY be used if the target existed in a previous window
- You cannot modify/adjust/shift something that was never initialized

**Common violations:**

a) **Adjusting a non-existent habit**
```json
// w2 tries to adjust "morning_meditation"
// But "morning_meditation" was never defined in initial_state or w1
{
  "op": "adjust",
  "habit_name": "morning_meditation",
  ...
}
```

b) **Modifying a non-existent attribute**
```json
// w3 tries to modify "user_subscriptions"
// But "user_subscriptions" was never in initial_state or added in w1-w2
{
  "op": "modify",
  "attribute_name": "user_subscriptions",
  ...
}
```

c) **Shifting a non-existent preference**
```json
// w2 tries to shift "exercise_style"
// But "exercise_style" was never in initial_state or w1
{
  "op": "shift",
  "preference_name": "exercise_style",
  ...
}
```

**How to check:**
1. For each `delete/modify` operation in window N, verify the attribute exists in initial_state OR was added in windows 1 to N-1
2. For each `adjust` operation in window N, verify the habit exists in initial_state OR was acquired in windows 1 to N-1
3. For each `shift`/`amplify`/`attenuate` operation in window N, verify the preference exists in initial_state OR was shifted in windows 1 to N-1

**How to fix:**
- Option A (Recommended): Add the missing item to initial_state with a baseline value, then keep the modification operation as-is
- Option B: Change the operation type from `delete/modify`/`adjust`/`shift` to `add`/`acquire`/`shift` (first introduction)

**Example fix (Option A - add to initial_state):**
```json
// BEFORE
// initial_state has no "morning_meditation" habit
// w2 has: {"op": "adjust", "habit_name": "morning_meditation", ...}

// AFTER
// Add to initial_state:
{
  "action": "meditate_seated",
  "frequency": "2_times_per_week",
  "timing": "7:00-7:15 AM on weekends",
  "context": "in a quiet corner of the bedroom",
  "description": "User practices basic mindfulness meditation twice weekly on weekend mornings"
}
// Keep w2's adjust operation as-is (now valid since habit exists in initial)
```



### Category 3: Missing Essential Items That Should Be Initialized

**What to look for:** Items that are essential for this user/domain but are missing from initial_state, especially when they're modified in later windows

**The rule:** If an item is **essential** (something a realistic person in this situation would already have) AND it's **evolved in later windows**, it MUST be initialized in initial_state

**Common violations:**

a) **No smartphone in initial_state for a modern adult**
```json
// Finances & Material Living domain
// initial_state has empty "user_owned_devices"
// w3 adds "iPhone 14" as first device
// PROBLEM: A working adult in 2024 would already own a phone
```

b) **No payment method for someone with income**
```json
// Finances & Material Living domain
// User has income but no bank account or payment methods in initial_state
// w2 adds first "Visa credit card"
// PROBLEM: How were they receiving income before?
```

**How to check:**
1. Look for items that appear for the first time in later windows via `add` operations - should they have existed from the start?

**Essential items by domain (examples):**
- Finances & Material Living: bank account, at least one payment method, housing-related items
- Health & Self-care: basic toiletries, bed/bedding, seasonally appropriate clothing
- Family & Close Relationships: communication devices if family is not co-located

**How to fix:**
- Add the missing essential item to initial_state with a realistic baseline value
- Update initial_state's summary to mention it
- If later windows modify this item, ensure the profile is consistent with the modification

**Example fix:**
```json
// BEFORE
// initial_state: empty "user_owned_devices" list
// w3: add ["iPhone 14 Pro (primary smartphone for work and personal use)"]

// AFTER
// Add to initial_state:
{
    "user_owned_devices": [
      "iPhone 12 (mid-range smartphone used for daily communication and work)"
    ]
}

// Update w3 to "modify" instead of "add":
{
  "op": "modify",
  "attribute_name": "user_owned_devices",
  "new_state": [
    "iPhone 14 Pro (upgraded smartphone with better camera for work presentations)"
  ],
  "reason": "Upgraded phone for improved camera quality needed for remote work presentations"
}
```


### Category 4: Direct Time Conflicts (Temporal Collision)

**What to look for:** Two or more activities scheduled at overlapping times when the user cannot physically do both

**Common violations:**

a) **Same exact time slot**
```json
// Domain A: "gym_session" every Wednesday 7:00-8:30 PM
// Domain B: "family_dinner" every Wednesday 7:00-8:00 PM
// CONFLICT: User cannot be at gym and family dinner simultaneously
```

b) **Overlapping time blocks**
```json
// Domain A: "morning_commute" weekdays 8:00-9:00 AM
// Domain B: "morning_exercise" weekdays 8:30-9:15 AM
// CONFLICT: Commute and exercise times overlap
```

c) **Multiple "daily" habits at same time**
```json
// Habit A: "morning_coffee_routine" daily 6:30-7:00 AM
// Habit B: "morning_dog_walk" daily 6:45-7:15 AM
// CONFLICT: Both are daily and times overlap
```

**How to check:**
1. Within each time window, list all habits with specific timing
2. Parse timing strings to identify start and end times
3. Check for overlaps between any two habits
4. Pay special attention to "daily" habits - they will conflict every day
5. Check across ALL domains, not just within one domain

**How to fix:**
- Option A: Shift one activity to a different time slot
- Option B: Reduce frequency of one activity (e.g., from "daily" to "3_times_per_week")
- Option C: Remove the lower-priority activity entirely if timing cannot be adjusted

**Example fix:**
```json
// BEFORE
// Habit A: "gym_session" Wednesday 7:00-8:30 PM (in Health & Wellness)
// Habit B: "family_dinner" Wednesday 7:00-8:00 PM (in Family & Close Relationships)

// AFTER (Option A: shift timing)
// Keep Habit A: "gym_session" Wednesday 5:30-7:00 PM (shifted earlier)
// Keep Habit B: "family_dinner" Wednesday 7:00-8:00 PM (unchanged, higher priority)

// Update the gym habit:
{
  "op": "adjust",
  "habit_name": "gym_session",
  "new_state": {
    "action": "strength_training",
    "frequency": "weekly",
    "timing": "Wednesday 5:30-7:00 PM",
    "context": "at local fitness center",
    "description": "Weekly strength training session moved earlier to accommodate family dinner time"
  },
  "reason": "Shifted to earlier time to avoid conflict with family dinner commitment"
}
```

### Category 5: Schedule Overload and Unrealistic Time Constraints

**What to look for:** While activities don't directly overlap, the overall schedule is implausibly packed or lacks required spacing/buffer time

**Common violations:**

a) **No spacing between activities**
```json
// Activity A: "evening_workout" ends at 7:00 PM
// Activity B: "family_dinner_prep" starts at 7:00 PM
// PROBLEM: No transition time (should have 15-30 min buffer for shower, travel, etc.)
```

b) **Single time slot overcrowding**
```json
// Saturday morning (9:00-11:00 AM):
//   - grocery_shopping (9:00-10:30 AM)
//   - family_breakfast_outing (9:00-11:00 AM)
//   - youth_soccer_practice (9:00-10:00 AM)
//   - home_cleaning_routine (8:00-10:00 AM)
//   - weekend_yoga_class (9:30-10:30 AM)
// PROBLEM: Five activities in same 2-hour window - impossible to do all
```

c) **Daily time budget exhaustion**
```json
// Total daily commitments:
//   - 8 hours work
//   - 1.5 hours commute
//   - 2 hours morning/evening routines
//   - 1.5 hours exercise
//   - 1 hour meal prep
//   - 1 hour family time
//   - 1 hour hobby
//   - 1 hour learning
//   - 8 hours sleep
// TOTAL: 25 hours (exceeds 24 hours in a day!)
```

d) **Frequency overlap at same time-of-day**
```json
// "Every weekday evening 6:00-8:00 PM":
//   - gym_session (daily, 6:00-7:30 PM)
//   - online_course (3x/week, 6:30-8:00 PM)
//   - family_dinner_prep (daily, 6:00-7:00 PM)
// PROBLEM: gym is daily, course is 3x/week, dinner is daily
// On days with course, user has 3 conflicting activities
```

**How to check:**
1. Map out a typical day/week with all habits across ALL domains
2. Calculate total time commitments including:
   - Work/sleep (assume 8 hours each minimum)
   - All habits with specific timing
   - Reasonable transition/buffer time (15-30 min between activities)
   - Meals (if not explicitly scheduled, assume 2-3 hours total daily)
3. Verify there's at least 2-3 hours of unscheduled buffer time per day
4. Check that weekends have some unstructured free time
5. Verify no time slot has more than 2-3 activities per week

**How to fix:**
- Priority ranking: Use basic profile to determine which activities are most important (core needs > social commitments > hobbies)
- Apply thinning strategies:
  - Reduce frequency (daily → 3-4x/week)
  - Shift to different time slots (spread across week)
  - Remove lower-priority activities
  - Combine activities where realistic (e.g., podcast during commute)

**Example fix:**
```json
// BEFORE (weekday evenings overloaded)
// - gym_session: daily 6:00-7:30 PM
// - online_course: 3x/week (Mon/Wed/Fri) 6:30-8:00 PM
// - family_dinner: daily 6:00-7:00 PM

// AFTER (thinned and reorganized)
// - gym_session: 4x/week (Tue/Thu/Sat/Sun) 6:00-7:30 PM
// - online_course: 2x/week (Mon/Wed) 8:00-9:30 PM (shifted later)
// - family_dinner: daily 6:30-7:30 PM (slightly later, more realistic)

// Updated operations:
{
  "op": "adjust",
  "habit_name": "gym_session",
  "new_state": {
    "action": "strength_and_cardio_workout",
    "frequency": "4_times_per_week",
    "timing": "Tuesday, Thursday, Saturday, Sunday 6:00-7:30 PM",
    "context": "at local fitness center",
    "description": "Reduced to 4x weekly to accommodate other evening commitments and avoid overload"
  },
  "reason": "Reduced frequency to create more balanced weekly schedule with time for family and learning"
}
```



### Category 6: Attribute Conflicts Across Domains

**What to look for:** The same attribute appearing in multiple domains with contradictory or overlapping values

**Two sub-types:**

**6a. Singular Attribute Conflicts**
**Definition:** Same attribute key exists in multiple domains with DIFFERENT values in the same window

```json
// Work & Education domain @ initial_state
"job_title": ["Director of Product Management"]

// Finances & Material Living domain @ initial_state  
"job_title": ["Senior Product Manager"]

// CONFLICT: User cannot have two different job titles simultaneously
```

**6b. Collection Item Conflicts**
**Definition:** Same attribute key exists in multiple domains, and the collections contain:
- Contradictory items: Items from mutually exclusive categories (user can only have ONE)
- Overlapping items: Exact duplicates appearing in multiple domains

**Common exclusive categories:**
- Smartphones: user has one primary phone (iPhone 14 OR Pixel 7, not both)
- Laptops: user has one primary laptop (MacBook Pro OR ThinkPad, not both)
- Tablets, fitness trackers, cars, primary residence, etc.

**Examples:**

```json
// CONTRADICTORY ITEMS (mutually exclusive)
// Technology & Digital Life domain:
"user_owned_devices": ["iPhone 14", "MacBook Pro"]

// Work & Education domain:
"user_owned_devices": ["Pixel 7", "ThinkPad X1"]

// CONFLICT: User cannot have both iPhone 14 AND Pixel 7 (competing phones)
// CONFLICT: User cannot have both MacBook Pro AND ThinkPad X1 (competing laptops)
```

```json
// OVERLAPPING ITEMS (exact duplicates)
// Finances & Material Living domain:
"user_subscriptions": ["Netflix", "Spotify", "NYT Digital"]

// Technology & Digital Life domain:
"user_subscriptions": ["Netflix", "Adobe Creative Cloud"]

// CONFLICT: "Netflix" appears in both domains (overlap/redundancy)
```

**How to check:**
1. Identify all attribute keys that appear in multiple domains
2. For singular attributes (job_title, residence, etc.), verify values match across domains
3. For collection attributes (owned_devices, subscriptions, etc.):
   - List all items across domains
   - Identify contradictory items (same product category, different brands/models)
   - Identify overlapping items (exact same item in multiple domains)
4. Cross-reference with basic user profile to determine most reasonable values

**How to fix:**

**For singular conflicts:**
- Choose the most authoritative domain (e.g., Work & Education owns job_title)
- Update all other domains to use the canonical value

**For contradictory items:**
- Evaluate which item is more reasonable based on:
  - User's basic profile (income, preferences, lifestyle)
  - Domain context (which domain has more relevant info)
  - Consistency with other attributes
- Remove the less reasonable item from its domain
- Keep only ONE item per exclusive category across all domains

**For overlapping items:**
- Determine most authoritative domain:
  - Dedicated domain (Technology & Digital Life for devices)
  - Financial tracking domain (Finances & Material Living for subscriptions)
  - Context-specific domain (Health & Wellness for fitness devices)
- Keep item in authoritative domain only
- Remove duplicates from all other domains

**Example fix:**
```json
// BEFORE
// Domain A (Technology & Digital Life):
"user_owned_devices": ["iPhone 14", "MacBook Pro", "AirPods Pro"]

// Domain B (Work & Education):
"user_owned_devices": ["Pixel 7", "iPad Pro", "AirPods Pro"]

// AFTER (assuming user prefers Apple ecosystem based on basic profile)
// Domain A (authoritative for devices):
"user_owned_devices": ["iPhone 14", "MacBook Pro", "AirPods Pro", "iPad Pro"]

// Domain B (remove contradictions and overlaps):
"user_owned_devices": []
// Or remove the attribute entirely if no unique items remain

// Reasoning:
// - Kept iPhone 14 (removed Pixel 7 - contradictory phone)
// - Kept AirPods Pro in Domain A only (removed from B - overlap)
// - Moved iPad Pro to Domain A (consolidate all devices in tech domain)
```



### Category 7: Short-Term Changes Without Follow-Up

**What to look for:** Changes motivated by temporary external factors (seasonal, event-driven, temporary circumstances) that are never reversed or adjusted when the factor ends

**The rule:** If a change is driven by a short-term external factor, there MUST be a follow-up operation in a later window that reverts, adjusts, or explicitly explains why it became permanent

**Common violations:**

a) **Seasonal changes without reversal**
```json
// w1 (winter): acquire "daily_aggressive_hydration_habit"
// reason: "combat dry winter air"
// w3 (summer): habit still exists unchanged
// PROBLEM: Summer humidity should reduce need for aggressive hydration
```

b) **Event-driven habits not dropped**
```json
// w2 (July-August): acquire "evening_olympic_viewing"
// reason: "watch Paris Olympics coverage"
// w3 (September-November): habit still exists
// PROBLEM: Olympics ended in August, habit should be dropped
```

c) **Temporary circumstance changes**
```json
// w2 (heatwave): shift preference to "indoor_exercise_only"
// reason: "extreme heat makes outdoor exercise unsafe"
// w3 (normal weather): preference unchanged
// PROBLEM: Should shift back to original preference when weather normalizes
```

**How to check:**
1. Scan all operation `reason` fields for keywords indicating short-term factors:
   - Seasonal: "winter", "summer", "spring", "fall", "seasonal", "holiday"
   - Events: "Olympics", "festival", "conference", "wedding", "vacation"
   - Temporary: "heatwave", "construction", "temporary", "while", "during"
2. For each short-term change in window N, verify that window N+1 or later includes:
   - A rollback operation (drop/adjust/attenuate)
   - OR explicit reasoning why it became permanent
3. Verify timing is realistic:
   - Seasons: ~3 months
   - Major events (Olympics): ~2-3 weeks
   - Weather events (heatwave): days to weeks
   - Holidays: 1-2 weeks

**How to fix:**
- Add a new operation in the appropriate later window to revert/adjust the temporary change
- Update that window's summary to mention the rollback
- Ensure the reasoning connects back to the original temporary factor ending

**Example fix:**
```json
// BEFORE
// w1 (Dec-Feb, winter):
{
  "op": "acquire",
  "habit_name": "aggressive_hydration_routine",
  "new_state": {
    "action": "drink_water_on_schedule",
    "frequency": "daily_every_2_hours",
    "timing": "throughout_waking_hours",
    "context": "using 1L water bottle with time markers",
    "description": "Structured hydration routine to combat dry winter air and maintain health"
  },
  "reason": "Winter indoor heating causes dry air leading to dehydration"
}

// w3 (Jun-Aug, summer): no follow-up

// AFTER
// Keep w1 as-is, add to w3:
{
  "op": "adjust",
  "habit_name": "aggressive_hydration_routine",
  "new_state": {
    "action": "drink_water_when_thirsty",
    "frequency": "as_needed",
    "timing": "throughout_the_day",
    "context": "standard water bottle kept nearby",
    "description": "Relaxed hydration approach as summer humidity reduces dehydration risk"
  },
  "reason": "Summer humidity and natural perspiration reduce need for aggressive scheduled hydration"
}

// Also update w3 summary:
"summary": "User adjusts hydration routine to seasonal needs, reducing from aggressive winter schedule to natural summer approach. [... other changes ...]"
```


### Category 8: Cross-Window Inconsistencies and Narrative Coherence

**What to look for:** Logical inconsistencies or narrative incoherence across the temporal sequence

**Common violations:**

a) **Contradictory progressions**
```json
// w1: drop "morning_meditation" reason: "too time-consuming"
// w3: acquire "morning_meditation" with same timing
// PROBLEM: No explanation for why user changed mind
```

b) **Unmotivated changes**
```json
// initial_state: "prefers_outdoor_exercise"
// w2: shift to "prefers_indoor_gym_workouts"
// reason: "trying new workout style"
// PROBLEM: Too vague - what actually motivated this major preference shift?
```

c) **Missing causal connections**
```json
// w1: acquire expensive camera equipment
// w2: acquire photography habit
// PROBLEM: Should acknowledge camera purchase enabled the new habit
```

d) **Window descriptions don't align with changes**
```json
// w2 window_description: "User focused on financial savings this quarter"
// w2 changes: acquires expensive gym membership, luxury subscription services
// PROBLEM: Changes contradict the stated focus on savings
```

e) **Unrealistic progression pace**
```json
// w1: acquire "beginner_yoga" 1x/week
// w2: "intermediate_yoga" 3x/week
// w3: "advanced_yoga_instructor_certification"
// PROBLEM: Too rapid progression from beginner to instructor (unrealistic timeline)
```

**How to check:**
1. Read through the entire profile narrative sequentially
2. Verify each window_description aligns with the actual changes in that window
3. Check that changes build on previous states logically
4. Look for abrupt reversals without explanation
5. Verify progression pace is realistic (skills take time to develop, preferences don't flip randomly)
6. Ensure reasons reference relevant context (prior states, window factors, basic profile)

**How to fix:**
- Add missing context to reasons (reference prior states or external factors)
- Revise window_description to accurately reflect the changes
- Add intermediate steps if progression is too rapid
- Provide clear motivation for reversals or major shifts
- Ensure summaries connect changes to window_description's driving factors

**Example fix:**
```json
// BEFORE
// w2 window_description: "User explores new hobbies this quarter"
// w2: acquire "advanced_photography" with professional equipment
// PROBLEM: No prior photography experience in w1

// AFTER
// Revise w2 window_description:
"window_description": "User discovers interest in photography after receiving a camera as a gift, beginning to explore this new creative hobby with basic equipment"

// Adjust w2 habit to be beginner-appropriate:
{
  "op": "acquire",
  "habit_name": "beginner_photography_practice",
  "new_state": {
    "action": "practice_basic_photography",
    "frequency": "2_times_per_week",
    "timing": "weekend afternoons",
    "context": "at local parks with entry-level camera",
    "description": "Beginner photography practice exploring composition and lighting basics"
  },
  "reason": "Received camera as gift and developing interest in photography as creative outlet"
}
```
